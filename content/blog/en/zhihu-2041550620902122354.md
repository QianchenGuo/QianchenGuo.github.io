## 1. Implicit Multithreading on CPU

**Automatic multithreading on the CPU side.** The advantage is that it requires minimal effort; the disadvantage is that it only accelerates the parts supported by MATLAB [built-in functions](https://zhida.zhihu.com/search?content_id=275432991&content_type=Article&match_order=1&q=%E5%86%85%E7%BD%AE%E5%87%BD%E6%95%B0&zhida_source=entity), and offers limited help for your own large `for` loops. [MathWorks](https://zhida.zhihu.com/search?content_id=275432991&content_type=Article&match_order=1&q=MathWorks&zhida_source=entity)'s parallel computing selection guide also lists "[vectorized code](https://zhida.zhihu.com/search?content_id=275432991&content_type=Article&match_order=1&q=%E5%90%91%E9%87%8F%E5%8C%96%E4%BB%A3%E7%A0%81&zhida_source=entity)" and "using automatic parallel support in MathWorks products" as foundational approaches to accelerating computations.

### 1.1 Vectorized Computation: The Most Fundamental and Important "Implicit Parallelism"

MATLAB excels at array and [matrix operations](https://zhida.zhihu.com/search?content_id=275432991&content_type=Article&match_order=1&q=%E7%9F%A9%E9%98%B5%E8%BF%90%E7%AE%97&zhida_source=entity). Often, the first step in "parallel acceleration" is not immediately writing `parfor` or moving to GPU, but rewriting element-wise, sample-wise, or column-wise `for` loops into [matrix expressions](https://zhida.zhihu.com/search?content_id=275432991&content_type=Article&match_order=1&q=%E7%9F%A9%E9%98%B5%E8%A1%A8%E8%BE%BE%E5%BC%8F&zhida_source=entity). Once vectorized, MATLAB can call optimized numerical libraries at the low level, and many [linear algebra](https://zhida.zhihu.com/search?content_id=275432991&content_type=Article&match_order=1&q=%E7%BA%BF%E6%80%A7%E4%BB%A3%E6%95%B0&zhida_source=entity) operations automatically leverage multithreaded CPUs.

For example, an inefficient approach is:

```text
N = size(X,2);
y = zeros(1,N);

for i = 1:N
    y(i) = sum(X(:,i).^2);
end
```

The vectorized approach is:

```text
y = sum(X.^2, 1);
```

The advantages of vectorization are concise code, typically fast execution, and no need for the [Parallel Computing Toolbox](https://zhida.zhihu.com/search?content_id=275432991&content_type=Article&match_order=1&q=Parallel+Computing+Toolbox&zhida_source=entity) or manual worker management. The disadvantage is that not all problems are easily vectorized—especially when each loop iteration involves complex logic, file I/O, simulation calls, or many conditional branches.

In MATLAB, vectorization is usually the first step before any other parallel approach, because it benefits subsequent acceleration methods such as CPU multithreading, GPU, and [distributed arrays](https://zhida.zhihu.com/search?content_id=275432991&content_type=Article&match_order=1&q=distributed+arrays&zhida_source=entity).

### 1.2 Automatic Multithreading in MATLAB Built-in Functions

Many MATLAB built-in functions are themselves multithreaded, such as [matrix multiplication](https://zhida.zhihu.com/search?content_id=275432991&content_type=Article&match_order=1&q=%E7%9F%A9%E9%98%B5%E4%B9%98%E6%B3%95&zhida_source=entity), matrix decompositions, [FFT](https://zhida.zhihu.com/search?content_id=275432991&content_type=Article&match_order=1&q=FFT&zhida_source=entity), some statistical functions, and [image processing](https://zhida.zhihu.com/search?content_id=275432991&content_type=Article&match_order=1&q=%E5%9B%BE%E5%83%8F%E5%A4%84%E7%90%86&zhida_source=entity) functions. The user's code appears as a single line, but the underlying implementation may already utilize multiple CPU cores.

Typical examples:

```text
C = A * B;
[V,D] = eig(A);
R = chol(A);
Y = fft(X);
```

The key characteristic is that **you don't need to explicitly write [parallel code](https://zhida.zhihu.com/search?content_id=275432991&content_type=Article&match_order=1&q=%E5%B9%B6%E8%A1%8C%E4%BB%A3%E7%A0%81&zhida_source=entity)**. As long as your computations fall on MATLAB's high-performance built-in functions, you may automatically benefit from multi-core CPUs.

The drawback is equally clear: if your code is dominated by custom `for` loops, sample-by-sample simulations, or complex if-else logic, MATLAB will not automatically split these loops across multiple CPU cores. In such cases, you need `parfor`, `parfeval`, or other explicit [parallel approaches](https://zhida.zhihu.com/search?content_id=275432991&content_type=Article&match_order=1&q=%E5%B9%B6%E8%A1%8C%E6%96%B9%E5%BC%8F&zhida_source=entity).

## 2. Explicit Multi-Worker Parallelism on CPU

This requires the Parallel Computing Toolbox. The essence is distributing tasks to multiple MATLAB workers for execution. Workers can be multiple processes/threads on your local machine or on a cluster. According to the MathWorks user guide, MATLAB workers are background MATLAB computational engines without a graphical interface; you can distribute tasks to these workers for parallel execution. Local workers can exploit desktop multi-core CPUs, and this can also scale to clusters.

### 2.1 `parfor`: CPU Loop-Level Parallelism

`parfor` is the most commonly used CPU parallel approach in MATLAB. It distributes independent [iterations](https://zhida.zhihu.com/search?content_id=275432991&content_type=Article&match_order=1&q=%E8%BF%AD%E4%BB%A3&zhida_source=entity) of an ordinary `for` loop to multiple workers for simultaneous execution. The MathWorks documentation also explicitly states that `parfor` is suitable for loops with many iterations, where individual iterations are relatively slow, and where iterations are mutually independent.

Standard form:

```text
for i = 1:N
    y(i) = expensiveFunction(x(i));
end
```

Parallel form:

```text
parpool("local", 8)

parfor i = 1:N
    y(i) = expensiveFunction(x(i));
end
```

`parfor` suits scenarios like this:

```text
parfor i = 1:N
    result(i) = runSimulation(param(i));
end
```

Examples include many independent simulations, multi-[parameter sweeps](https://zhida.zhihu.com/search?content_id=275432991&content_type=Article&match_order=1&q=%E5%8F%82%E6%95%B0%E6%89%AB%E6%8F%8F&zhida_source=entity), multi-random-seed experiments, and cases where each sample independently calls an [expensive function](https://zhida.zhihu.com/search?content_id=275432991&content_type=Article&match_order=1&q=%E8%80%97%E6%97%B6%E5%87%BD%E6%95%B0&zhida_source=entity).

The advantage of `parfor` is the relatively low modification cost—especially when an existing `for` loop is present, you often only need to change `for` to `parfor` and adjust variable declarations. The drawback is scheduling overhead: if each loop iteration takes only a few milliseconds or less, `parfor` may actually be slower. Additionally, iterations must be essentially independent with no complex iteration-to-iteration dependencies.

### 2.2 `parfeval`: CPU Task-Level Asynchronous Parallelism

`parfeval` is asynchronous parallelism. Unlike `parfor`, which "executes a loop together and waits for all iterations to finish," `parfeval` submits a function call to a worker, allowing the main MATLAB session to continue executing other code, and later retrieves results with `fetchOutputs`. MathWorks distinguishes `parfeval` from `parfor` and `[spmd](https://zhida.zhihu.com/search?content_id=275432991&content_type=Article&match_order=1&q=spmd&zhida_source=entity)` as different [parallel programming models](https://zhida.zhihu.com/search?content_id=275432991&content_type=Article&match_order=1&q=%E5%B9%B6%E8%A1%8C%E7%BC%96%E7%A8%8B%E6%A8%A1%E5%9E%8B&zhida_source=entity).

Basic form:

```text
parpool("local", 4)

f1 = parfeval(@myFunction, 1, input1);
f2 = parfeval(@myFunction, 1, input2);

% The main thread can continue doing other things

out1 = fetchOutputs(f1);
out2 = fetchOutputs(f2);
```

It is suitable for:

```text
futures = parallel.FevalFuture.empty(N,0);

for i = 1:N
    futures(i) = parfeval(@runOneExperiment, 1, configs{i});
end

for i = 1:N
    [idx, value] = fetchNext(futures);
    fprintf("Task %d finished\n", idx);
end
```

The advantage of `parfeval` is flexibility—it suits tasks with uneven execution times, scenarios where you want to process results as they arrive, and running multiple experiments in the background. The drawback is that code organization is somewhat more complex than `parfor`, and it is not suitable if tasks require frequent communication with each other.

| Comparison | parfor | parfeval |
| --- | --- | --- |
| Execution mode | [Parallel loop](https://zhida.zhihu.com/search?content_id=275432991&content_type=Article&match_order=1&q=%E5%B9%B6%E8%A1%8C%E5%BE%AA%E7%8E%AF&zhida_source=entity), typically waits for full completion | [Asynchronous tasks](https://zhida.zhihu.com/search?content_id=275432991&content_type=Article&match_order=1&q=%E5%BC%82%E6%AD%A5%E4%BB%BB%E5%8A%A1&zhida_source=entity), can fetch results while running |
| Suitable structure | Many homogeneous loop iterations | Multiple heterogeneous tasks, uneven task durations |
| Code complexity | Lower | Higher |
| Result retrieval | Unified after loop ends | fetchNext / fetchOutputs |
| Typical use cases | Parameter sweeps, independent sample evaluation | Background experiments, [multi-task scheduling](https://zhida.zhihu.com/search?content_id=275432991&content_type=Article&match_order=1&q=%E5%A4%9A%E4%BB%BB%E5%8A%A1%E8%B0%83%E5%BA%A6&zhida_source=entity), asynchronous UI updates |

`parfor` is more like "parallelizing one large loop"; `parfeval` is more like "submitting many tasks to a background queue."

### 3\. `backgroundPool`: Background Thread Pool

`backgroundPool` is MATLAB's background parallel environment, allowing code to run in the background while the main MATLAB session remains responsive. According to MathWorks documentation, `backgroundPool` is backed by thread workers. Even without a Parallel Computing Toolbox license, you can use one background thread worker; with the toolbox, additional capabilities are available.

Typical usage:

```text
f = parfeval(backgroundPool, @longFunction, 1, input);
% Main MATLAB session remains interactive for plotting, editing, etc.
result = fetchOutputs(f);
```

It is well-suited for background tasks such as saving large files, preprocessing data, asynchronous data loading, background plotting, or computing results that are not urgently needed. It is not suitable for large-scale numerical computations that require significant process-level parallelism; for those, `parpool` with `parfor` or `parfeval` is typically the better choice.

### 4\. spmd: Explicit Multi-Worker Parallelism

spmd stands for Single Program, Multiple Data. It executes the same code block simultaneously across multiple workers, with each worker able to identify itself via `spmdIndex` or `labindex` to process different data. MathWorks documentation indicates that code inside an spmd block runs on all workers of the parallel pool.

Example:

```text
parpool(4)

spmd
    idx = spmdIndex;
    localResult = idx^2;
end
```

spmd is suitable for parallel logic more complex than what `parfor` can express, such as:

```text
Each worker maintains its own state
Each worker processes a distinct chunk of data
Communication between workers is required
Use of codistributed / distributed arrays
Manual allocation across multiple GPUs
```

The advantages of spmd are its flexibility, power, and control; the disadvantages are higher code complexity, requiring you to explicitly handle data partitioning, communication, synchronization, and result aggregation. For ordinary independent loops, prefer `parfor`; only consider spmd when `parfor` cannot express your computational structure.

| Aspect | parfor | spmd |
| --- | --- | --- |
| Abstraction level | High | Low |
| Suitable tasks | Independent loops | Collaborative tasks across workers |
| Data communication | Automatically handled by MATLAB | Explicitly controlled by user |
| Programming difficulty | Lower | Higher |
| Flexibility | Moderate | Very high |
| Distributed arrays | Not a focus | Excellent fit |
| Multi-GPU control | Inflexible | More flexible |

### 5\. Leveraging MEX

MEX is an interface mechanism that allows MATLAB to call native C/C++/Fortran code. If C++ MEX code incorporates OpenMP, C++ threads, or TBB, this constitutes CPU multithreaded parallelism. This parallelism does not rely on MATLAB's `parfor`; instead, your C++ code spawns threads internally within the MEX file. If your MEX code calls multithreaded math libraries such as BLAS, LAPACK, MKL, or Eigen, that also falls under CPU numerical library parallelism.

## III. GPU Parallelism

CPU parallelism is better suited for scenarios involving complex control flow, independent tasks, extensive branching, and tasks with relatively long execution times—for example, numerous independent simulations, finite element computations, multi-parameter sweeps, file processing, or invoking external programs. GPU parallelism is better suited for scenarios involving regular data structures, compute-intensive operations, and the same operation applied to vast numbers of elements—for example, large matrices, large arrays, images, convolutions, deep learning, Monte Carlo simulations, and batch function evaluations. In short: Multicore CPUs excel at "running many complex tasks in parallel"; GPUs excel at "applying the same simple/regular operation to massive amounts of data simultaneously."

MathWorks examples categorize GPU computing into three approaches: first, converting input data to `gpuArray`; second, using `arrayfun` on `gpuArray`s; and third, running existing CUDA/C++ code via `parallel.gpu.CUDAKernel`.

### 1\. `gpuArray`: High-Level GPU Array Parallelism

`gpuArray` is the core way to use GPUs in MATLAB. Without requiring you to write CUDA kernels, it places arrays into GPU memory, and MATLAB's overloaded functions automatically invoke GPU implementations. Subsequently, supported MATLAB functions operate directly on the GPU. MathWorks documentation states that many MATLAB and toolbox functions automatically execute on the GPU when their inputs are `gpuArray`s, which represent arrays stored on the GPU.

Basic form:

```text
A = gpuArray(rand(5000,5000));
B = gpuArray(rand(5000,5000));

C = A * B;        % Executes on the GPU
C_cpu = gather(C); % Retrieves data back to the CPU
```

You can also directly create GPU random arrays:

```text
X = gpuArray.randn(1000, 100000, "single");
Y = sum(X.^2, 1);
```

GPUs are suitable for large-batch, structurally regular, array-intensive computations such as large matrix multiplications, convolutions, FFTs, large-scale element-wise operations, deep learning, image processing, and large-scale Monte Carlo simulations.

Scenarios unsuitable for GPUs are equally important: if the data size is very small, if frequent `gather` operations back to the CPU are required at each step, or if the computation involves many functions not supported on GPUs, performance may degrade rather than improve. `gather` transfers GPU or distributed data back to the local workspace; the documentation explicitly notes that `gather` transfers `gpuArray` elements from the GPU to the local workspace.

| Aspect | parfor | gpuArray |
| --- | --- | --- |
| Hardware | Multicore CPU | NVIDIA GPU |
| Parallelism granularity | Loop iteration level | Array element / matrix operation level |
| Suitable tasks | Independent function calls, simulations, parameter sweeps | Large-scale array computations |
| Programming style | Change `for` to `parfor` | Convert data to `gpuArray` |
| Data constraints | Data transfer between workers | Limited by GPU memory |
| Overheads | Worker startup and communication | CPU-GPU data transfer |
| Small task performance | Can be poor | Can be poor |
| Large regular computations | Inferior to GPU | Usually excellent |
| Complex branching | Relatively suitable | Less suitable |

A common misconception is that combining `parfor` with GPU is always faster. With a single GPU, multiple CPU workers contending for the same GPU often leads to slower performance. A better approach is typically either CPU `parfor` or a single MATLAB process sending one large array to the GPU for batch computation.

### 2\. `arrayfun`, `pagefun`: GPU Element-Wise/Page-Wise Parallelism

Beyond standard `gpuArray` operations, MATLAB supports finer-grained GPU programming constructs. For instance, `arrayfun` applies an element-wise function to GPU arrays; MathWorks documentation states that `arrayfun` fully supports GPU arrays, meaning it can run on the GPU when inputs are `gpuArray`s.

Example:

```text
x = gpuArray.linspace(-5,5,1e7);
y = arrayfun(@(t) sin(t)^2 + cos(t)^2, x);
```

For many page-wise matrix operations, you can also use batch-oriented approaches, such as performing matrix multiplication, matrix decomposition, or other batch operations on each page of a 3-D array. This suits scenarios involving "many small matrices of the same size computed simultaneously."

These approaches use the GPU more efficiently than standard vectorization but require relatively regular function forms, avoiding overly complex logic at the MATLAB interpreter level.

### 3\. CUDA Kernels: Low-Level GPU Programming

The methods introduced above are the more common, high-level approaches to parallelism in MATLAB. MATLAB does, however, support running CUDA/PTX code directly, primarily through two routes:

**(1) parallel.gpu.CUDAKernel**

The general workflow is:

```text
k = parallel.gpu.CUDAKernel('myKernel.ptx','myKernel.cu');
k.ThreadBlockSize = [256 1 1];
k.GridSize = [ceil(N/256) 1 1];

out = feval(k, in, out, N);
```

MathWorks documentation explains that you can compile PTX from a `.cu` file and then create a kernel object using `parallel.gpu.CUDAKernel` to execute it. This approach is suitable when you already have a CUDA kernel or when MATLAB's `gpuArray` cannot express your computation.

**(2) mexcuda**

`mexcuda` compiles CUDA C++ MEX files using NVIDIA's `nvcc` compiler, allowing MEX files to define and launch GPU kernels, as well as read and write MATLAB GPU arrays. This approach offers greater flexibility, as you can write full C++/CUDA host code and kernel code. MathWorks documentation also notes that MEX files are generally more flexible than `CUDAKernel` objects.

High-level direct GPU usage: `gpuArray` — you don't write CUDA kernels; MATLAB automatically invokes GPU-version functions. Characteristics: high-level, simple, fast development, dependent on GPU-enabled MATLAB functions. Low-level direct GPU usage: CUDA kernels / CUDA MEX — this is CUDA-style programming invoked through MATLAB. Characteristics: low-level, flexible, performance-controllable, complex development requiring understanding of CUDA threads, blocks, grids, memory access, and synchronization. In short, `gpuArray` has MATLAB writing the GPU version for you; CUDA kernels require you to write the GPU code yourself.

| Aspect | gpuArray | CUDA kernel / CUDA MEX |
| --- | --- | --- |
| Abstraction level | High | Low |
| Requires writing CUDA | No | Yes |
| Development difficulty | Low | High |
| Performance control | Limited | Very strong |
| Debugging difficulty | Lower | Higher |
| Suitable tasks | Array operations already supported by MATLAB | Special computations difficult to express or insufficiently performant in MATLAB |
| Data objects | MATLAB `gpuArray` | CUDA device memory / MATLAB GPU MEX API |
| Typical entry points | `gpuArray`, `arrayfun` | `parallel.gpu.CUDAKernel`, `mexcuda` |

## 4. Big Data / Distributed / Clusters

Generally, individual algorithm developers may not use these much?

### 1. distributed arrays / codistributed arrays: Distributed Arrays

When an array is too large to fit in the memory of a single worker or a single machine, or when you want multiple workers to jointly process a large array, you can use distributed arrays or codistributed arrays. The MathWorks documentation classifies distributed arrays as one approach for parallel processing of big data, and notes that arrays can be distributed across multiple workers.

Conceptually, this can be understood as:

```text
Ordinary array: the entire matrix resides in a single MATLAB process
Distributed array: the matrix is partitioned into chunks distributed across multiple workers
```

Suitable for: very large matrices, large-scale linear algebra, data exceeding single-machine memory, and multi-worker collaborative processing of large arrays.

The downside is higher programming complexity, as many operations involve inter-worker communication. Communication overhead can be significant, so this approach only pays off when the data scale is large enough and the computation is heavy enough.

| Comparison | gpuArray | distributed arrays |
| --- | --- | --- |
| Target hardware | Single GPU or multiple GPUs | Multiple CPU workers / cluster |
| Data location | GPU memory | Memory across multiple workers |
| Main bottleneck | GPU memory, CPU-GPU transfer | Worker communication, network/memory |
| Suitable tasks | Large-scale regular numerical computation | Very large arrays, distributed data |
| Programming difficulty | Medium | High |
| Suitable for small tasks | No | No |

gpuArray addresses "high compute density, well-suited for GPU"; distributed arrays address "data too large, needs distributed storage and computation."

### 2. tall arrays / datastore / mapreduce: Big Data Streaming Parallelism

`tall arrays` are primarily for cases where data is too large to fit into memory at once. They are often used together with `datastore` to read and process data in chunks. The MathWorks documentation groups tall arrays, datastores, and mapreduce under Big Data Processing for parallel analysis of large datasets.

Typical scenario:

```text
ds = datastore("large_folder/*.csv");
T = tall(ds);

summary = gather(mean(T.Var1));
```

`tall arrays` are suitable for: very large tables, log data, many files, data that cannot be read into memory all at once, data preprocessing, and statistical analysis.

They are not suitable for small-scale numerical optimization or real-time iterative computation. Their strength lies in handling "very large data," not "single computations that are very complex."

| Comparison | tall arrays | distributed arrays |
| --- | --- | --- |
| Primary purpose | Process data that cannot be read into memory at once | Distribute arrays across multiple worker memories |
| Data source | Files, datastore, large tables | Existing large arrays or distributed computing |
| Execution model | Lazy evaluation, gather at the end | Collaborative computation across workers |
| Typical tasks | Large-scale data cleaning, statistics, table processing | Large-scale matrix/array computation |
| User experience | Similar to table/array operations | More oriented toward parallel numerical computing |

tall arrays are more like a "big data analytics tool"; distributed arrays are more like a "distributed numerical computing tool."

### 3. `batch`: Background/Cluster Batch Processing

`batch` is used to submit a MATLAB function to run in the background or on a cluster. It is suitable for long-running tasks, parameter sweeps, paper experiments, and overnight batch runs. The MathWorks Parallel Computing Toolbox documentation also describes batch processing as the capability to "offload function execution to the background."

Illustration:

```text
job = batch(@myLongExperiment, 1, {config});
wait(job)
result = fetchOutputs(job);
```

The advantage of `batch` is that tasks can run outside the current interactive MATLAB session, making it suitable for long tasks and clusters. The downside is poor interactivity—it is not suitable for development phases where you need to inspect results at each step and tune parameters.

### 4. MATLAB Parallel Server / Cluster: Cluster Parallelism

If local CPU/GPU resources are insufficient, you can extend Parallel Computing Toolbox code to a cluster or the cloud. Typically, MATLAB Parallel Server enables `parfor`, `batch`, `spmd`, and other constructs to run in multi-node environments. The official Parallel Computing Toolbox page also states that it can leverage multicore desktops, GPUs, clusters, and cloud resources for compute-intensive tasks.

Suitable for: large parameter sweeps, large-scale simulations, multi-random-seed experiments, large-scale data processing, multi-GPU / multi-node tasks.

Not suitable for: small-scale scripts, frequent interactive debugging, and latency-sensitive tasks.

Cluster parallelism is not "automatically faster"—it requires consideration of data transfer, task scheduling, queue waiting, file systems, and other issues.

## 5. Horizontal Comparison

Below is a horizontal comparison across several dimensions.

### 1. Comparison by Ease of Use

| Approach | Ease of Use | Notes |
| --- | --- | --- |
| Vectorization | Low to medium | Requires rethinking code structure, but no Parallel Computing Toolbox needed |
| Built-in function auto-multithreading | Low | Essentially no management needed; just write matrix operations |
| gpuArray | Medium | Must pay attention to GPU-supported functions, memory, gather |
| parfor | Medium | Loops must be independent; variable classification must follow the rules |
| parfeval | Medium to high | Must manage futures, asynchronous results, error handling |
| backgroundPool | Medium | Suitable for background tasks; computation scale should generally not be too large |
| spmd | High | Must manage workers, communication, and data distribution yourself |
| distributed arrays | High | Must understand distributed data and communication costs |
| tall arrays | Medium | Friendly for large tables, but the execution model differs from ordinary arrays |
| batch / cluster | Medium to high | Requires configuring clusters, tasks, paths, and data dependencies |

### 2. Comparison by Task Type

| Task Type | Recommended Approach |
| --- | --- |
| Ordinary matrix operations | Vectorization + MATLAB auto-multithreading |
| Large matrices, large arrays, deep learning, image processing | gpuArray |
| Each sample independent and computationally expensive | parfor |
| Running multiple experiments concurrently | parfeval or batch |
| Background execution without blocking MATLAB | backgroundPool or parfeval |
| Workers need to communicate | spmd |
| Arrays too large for single-machine memory | distributed arrays |
| Very large files, huge tables, log data | tall arrays + datastore |
| Large-scale cluster/cloud experiments | batch + MATLAB Parallel Server |

### 3. Comparison by Overhead

| Approach | Primary Overhead | When It's Not Worthwhile |
| --- | --- | --- |
| Vectorization | Code rewrite cost | Hard to write when logic is overly complex |
| Auto-multithreading | Almost no explicit overhead | Limited benefit when code does not use built-in matrix operations |
| gpuArray | CPU-GPU data transfer, GPU startup, memory | Data too small, frequent gather, functions not GPU-supported |
| parfor | Worker startup, data distribution, result aggregation | Each loop iteration too fast, or data transfer too large |
| parfeval | Future management, task scheduling | Tasks too small or strongly synchronous |
| backgroundPool | Background thread scheduling | Insufficient for compute-intensive multi-process needs |
| spmd | Communication and synchronization | Ordinary loops that do not require worker communication |
| distributed arrays | Inter-worker communication | Data not large enough, or communication outweighs computation |
| tall arrays | Chunked I/O, lazy evaluation | When data fits easily in memory |
| batch / cluster | Queue, paths, file transfer | Small tasks, interactive debugging |

### 4. Comparison by Acceleration Potential

| Approach | Acceleration Potential | Notes |
| --- | --- | --- |
| Vectorization | High | For much MATLAB code, the biggest gains come from here |
| Auto-multithreading | Medium to high | Depends on whether high-performance built-in functions are invoked |
| gpuArray | Very high | Extremely powerful for large regular array computations |
| parfor | Medium to high | Great for independent heavy tasks; mediocre for light tasks |
| parfeval | Medium to high | Suitable for task-level parallelism; does not necessarily speed up a single task |
| backgroundPool | Low to medium | More for asynchrony than peak performance |
| spmd | Very high | Suitable for complex distributed or multi-GPU scenarios, but high programming cost |
| distributed arrays | Very high | Can break single-machine limits when data is large enough |
| tall arrays | Medium to high | Geared toward big data processing, not low-latency computation |
| cluster / batch | Very high | Suitable for large-scale experiments, but depends on hardware and scheduling systems |

### 5. How to Choose: A Practical Decision Table

| Your Question | Preferred Choice |
| --- | --- |
| Lots of ordinary for loops, but each iteration is fast | Vectorize first |
| Code is mainly matrix multiplication, decompositions, FFT | Use built-in functions first; explicit parallelism may not be needed |
| Each loop iteration is independent and time-consuming | parfor |
| Want to submit multiple experiments and process whichever finishes first | parfeval |
| Want background execution without blocking MATLAB | backgroundPool or parfeval |
| Large regular array operations, GPU-supported | gpuArray |
| An array is too large for single-machine memory | distributed arrays |
| Data files too large to read in one go | tall arrays + datastore |
| Need inter-worker communication or manual partitioning | spmd |
| Need to run hundreds of long experiments | batch / cluster |
