[Parallel computing](https://zhida.zhihu.com/search?content_id=276233685&content_type=Article&match_order=1&q=%E5%B9%B6%E8%A1%8C%E8%AE%A1%E7%AE%97&zhida_source=entity) can indeed achieve speedup in theory, but in practice one must also account for the scheduling of compute resources and the pressure of [memory allocation](https://zhida.zhihu.com/search?content_id=276233685&content_type=Article&match_order=1&q=%E5%86%85%E5%AD%98%E5%88%86%E9%85%8D&zhida_source=entity). Therefore, it is not the case that more aggressive [parallelization](https://zhida.zhihu.com/search?content_id=276233685&content_type=Article&match_order=1&q=%E5%B9%B6%E8%A1%8C%E5%8C%96&zhida_source=entity) or simply adding more threads makes an algorithm run faster. We need to match the computation granularity, synchronization cost, and [GPU](https://zhida.zhihu.com/search?content_id=276233685&content_type=Article&match_order=1&q=GPU&zhida_source=entity) occupancy to the actual task at hand, and choose an appropriate [CUDA](https://zhida.zhihu.com/search?content_id=276233685&content_type=Article&match_order=1&q=cuda&zhida_source=entity) topology and its parameters. At the same time, we should minimize useless data transfers on all sides—these can consume a significant amount of time. The former is reflected in stages 17, 18, and 34C4; the latter in stages 24, 30, and 34A.

## 1. What is a [CUDA topology](https://zhida.zhihu.com/search?content_id=276233685&content_type=Article&match_order=1&q=CUDA+%E6%8B%93%E6%89%91&zhida_source=entity)?

The CUDA execution hierarchy is roughly:

```text
Grid
  └── Block
        └── Warp
              └── Thread
```

Corresponding to the hardware:

```text
GPU
  └── SM / streaming multiprocessor
        └── concurrently schedules multiple blocks / warps
              └── 32 threads within a warp execute in lockstep
```

The most important concepts are:

| Level | Role |
| --- | --- |
| thread | The [thread](https://zhida.zhihu.com/search?content_id=276233685&content_type=Article&match_order=2&q=%E7%BA%BF%E7%A8%8B&zhida_source=entity), the smallest [execution unit](https://zhida.zhihu.com/search?content_id=276233685&content_type=Article&match_order=1&q=%E6%89%A7%E8%A1%8C%E5%8D%95%E5%85%83&zhida_source=entity) |
| warp | A group of 32 threads; the actual scheduling unit |
| block | A group of threads that can share [shared memory](https://zhida.zhihu.com/search?content_id=276233685&content_type=Article&match_order=1&q=shared+memory&zhida_source=entity) and use \_\_syncthreads() |
| grid | All blocks in a single [kernel](https://zhida.zhihu.com/search?content_id=276233685&content_type=Article&match_order=1&q=kernel&zhida_source=entity) launch |
| SM | The hardware unit on the GPU that actually executes blocks / warps |

Previously, the fastest main topology was essentially: one thread = one candidate [trajectory](https://zhida.zhihu.com/search?content_id=276233685&content_type=Article&match_order=1&q=trajectory&zhida_source=entity). That is: `k = blockIdx.x * blockDim.x + threadIdx.x;` Each candidate independently computes one trajectory.

If `K = 1536`, then there are 1536 trajectories that can run in parallel on the GPU. This [granularity](https://zhida.zhihu.com/search?content_id=276233685&content_type=Article&match_order=2&q=%E7%B2%92%E5%BA%A6&zhida_source=entity) is actually well suited to the GPU, because trajectories are completely independent of each other—no synchronization or communication is needed.

So the original [parallelization strategy](https://zhida.zhihu.com/search?content_id=276233685&content_type=Article&match_order=1&q=%E5%B9%B6%E8%A1%8C%E6%96%B9%E5%BC%8F&zhida_source=entity) was: candidate-level parallelism.

**Advantages:** many threads, very little synchronization, good occupancy, each candidate independent, simple scheduling.

**Disadvantages:** the H time steps within each trajectory are still serial; within each time step, the passive dynamics is also computed by a single thread.

## 2. Why did Stage-17 become slower?

Stage-17 mainly used an aggressive launch/build profile:

```text
threads per block = 256
decode threads per block = 256
scan threads per block = 256
--use_fast_math
-O3
```

But it did not actually turn the core passive dynamics into cooperative parallelism. That is, the core bottleneck remains: a single thread serially computes the physics / passive dynamics within one trajectory.

The result: [thread organization](https://zhida.zhihu.com/search?content_id=276233685&content_type=Article&match_order=1&q=%E7%BA%BF%E7%A8%8B%E7%BB%84%E7%BB%87&zhida_source=entity) became more aggressive, register / local memory pressure increased, occupancy may have gotten worse, but the real work was not effectively split across parallel resources.

Your Stage-17 logs exactly confirm this: in the `balanced_h20` verification, `14B=1.1133s` and `17=1.1138s`—almost no speedup; in normal [MPC](https://zhida.zhihu.com/search?content_id=276233685&content_type=Article&match_order=1&q=MPC&zhida_source=entity), it actually became noticeably slower: `balanced_h20` shows `MeanStepSolveSec=2.4835s` and `MeanObjCudaEvalCostSec=2.4666s`. This indicates that Stage-17 mainly added scheduling/resource pressure rather than reducing the core computation.

A simplified way to understand it: Stage-17 = switching to a more aggressive execution style without actually changing the [algorithmic structure](https://zhida.zhihu.com/search?content_id=276233685&content_type=Article&match_order=1&q=%E7%AE%97%E6%B3%95%E7%BB%93%E6%9E%84&zhida_source=entity) of the heaviest computation. So it not only failed to solve the problem but may also have triggered: register spilling, increased [local memory](https://zhida.zhihu.com/search?content_id=276233685&content_type=Article&match_order=1&q=local+memory&zhida_source=entity) accesses, fewer warps/blocks resident on an SM, and worse cache behavior.

## 3. Why did Stage-18 become slower?

Stage-18 was the first to truly confront the core problem: refactoring the passive dynamics from *one thread = one trajectory* to *one block = one trajectory*, with 128 threads cooperating on a single trajectory. This direction is theoretically sound, but your measurements show that **the per-step workload of the current passive dynamics is not large enough to amortize the synchronization and occupancy costs of a 128-thread block.**

Your measurements:

```text
balanced:
scalar = 0.102s
block  = 0.273s
speedup = 0.375x

balanced_h20:
scalar = 0.128s
block  = 0.479s
speedup = 0.268x
```

This means block-coop is 2.7 to 3.7 times slower.

Several reasons:

1. **Reason A: Time recursion itself cannot be parallelized.** Only a *portion* of the computation *within each time step* can be parallelized—e.g., integration inside the beam/passive dynamics, matrix assembly, reductions. So the theoretical time is not `T / 128`; it is closer to: `T_new = serial part of time recursion + parallelizable part per step / 128 + sync overhead + shared memory overhead + occupancy loss`. If the parallelizable portion of each step is not large enough, these latter costs will exceed the benefit.
2. **Reason B: 128 threads/block reduces candidate parallelism.** Originally, 1 thread = 1 candidate, so one 128-thread block could accommodate 128 candidate threads. Now it becomes 128 threads = 1 candidate. The same 128 threads serve only one trajectory. This drastically reduces the number of candidates the GPU processes simultaneously. Although each trajectory gains internal parallelism, if that internal parallel work is not large enough, it is a net loss.
3. **`__syncthreads()` is expensive.** A block-coop passive solver requires a great deal of synchronization: `__syncthreads()`; threads must cooperate to write shared memory, perform reductions, and assemble [matrices](https://zhida.zhihu.com/search?content_id=276233685&content_type=Article&match_order=2&q=%E7%9F%A9%E9%98%B5&zhida_source=entity), and the next step must wait for all threads to finish. If each substep has multiple syncs and the horizon has 126 or 251 samples, the sync cost is amplified. Roughly: sync cost × number of syncs per step × H × K. This cost is substantial.
4. **The actual matrix sizes are too small.** Many [key matrices](https://zhida.zhihu.com/search?content_id=276233685&content_type=Article&match_order=1&q=%E5%85%B3%E9%94%AE%E7%9F%A9%E9%98%B5&zhida_source=entity) in the passive reduced dynamics are very small—not suitable for 128-thread cooperation. For example, a 3x3 solve involves only a handful of numbers. Using 128 threads for this results in most threads idling while thread 0 serially solves, and others wait at the barrier. Here, more threads is not better; the thread count must match the task scale.
5. **Shared memory / register pressure increases.** The block-coop version needs shared memory for intermediate quantities, increasing per-block resource usage. SM resources are limited: if each block is too heavy, fewer blocks run concurrently on an SM, occupancy drops, and the GPU cannot achieve full throughput.

## 4. What does correct parallelism look like?

**Stage-17 increased resource pressure but did not truly parallelize the core computation. Stage-18 truly parallelized part of the core computation, but the [parallel granularity](https://zhida.zhihu.com/search?content_id=276233685&content_type=Article&match_order=1&q=%E5%B9%B6%E8%A1%8C%E7%B2%92%E5%BA%A6&zhida_source=entity) was too coarse; the synchronization and occupancy losses of a 128-thread block outweighed the gains.**

The answer is not to retreat from parallelism, but to adopt a more suitable topology: **one warp = one candidate trajectory**.

A warp consists of 32 threads, not 128. Compared to a 128-thread block, it has lower synchronization cost; compared to a single thread, it offers more internal parallelism; compared to block-coop, it is lighter on occupancy; and within a warp, shuffle instructions can be used for reductions, reducing the need for extensive `__syncthreads()`. The topology becomes: one block = multiple warps, one warp = one trajectory. For example: 128 threads/block = 4 warps/block = 4 trajectories/block. This is much better than Stage-18:

- Stage-18: 128 threads/block → 1 trajectory/block
- Stage-19: 128 threads/block → 4 trajectories/block

This preserves candidate-level parallelism while still gaining intra-trajectory cooperation.

## 5. Stage-24: The backbone of the subsequent exact path?

Between Stage-20 and Stage-23, the main work centered on engineering cleanup around the CUDA rollout, workspace, static pack, history [buffer](https://zhida.zhihu.com/search?content_id=276233685&content_type=Article&match_order=1&q=buffer&zhida_source=entity), and the [MATLAB](https://zhida.zhihu.com/search?content_id=276233685&content_type=Article&match_order=1&q=MATLAB&zhida_source=entity)–CUDA interface. These stages resolved some call-chain and data-movement issues, but did not yet change the core structure of the evaluator. What truly stabilized the subsequent mainline was Stage-24.

The core idea of Stage-24 is:

```text
fused decode + rollout + cost
```

That is, instead of splitting control-parameter decode, trajectory integration, history writes, and cost computation into multiple independent CUDA/MATLAB phases, carry out as much as possible within a single fused CUDA evaluator.

Before this, the typical flow was closer to:

```text
Z compact parameters
  -> decode into full control sequence U
  -> rollout dynamics
  -> write global history
  -> compute release / hit / clear / cost from history
```

Although this decomposition is logically clean, it introduces several problems:

```text
1. More intermediate workspaces
2. More global memory reads/writes
3. More kernel launches
4. More MATLAB/CUDA call boundaries
5. Diagnostic and production paths tend to diverge
6. Exact path and fast path are hard to keep consistent over the long term
```

What Stage-24 did was to fuse these processes as much as possible into a single CUDA evaluator path. The candidate parameters `Z` are fed directly into the fused evaluator, which performs control decode, state advancement, release determination, history updates, and cost accumulation entirely within CUDA. The main computation path becomes:

```text
Z compact
  -> Stage-24 fused decode-rollout-cost evaluator
  -> J
```

Its value is not merely “fewer kernel launches”; more importantly, it fixes the semantics of the exact evaluator. All subsequent optimizations—including the Stage-30 native persistent, Stage-34B2 CUDA [Graph](https://zhida.zhihu.com/search?content_id=276233685&content_type=Article&match_order=1&q=Graph&zhida_source=entity), the Stage-34C exact-preserving squeeze, and block-size tuning—revolve around this Stage-24 fused exact evaluator.

In other words, Stage-24 is the infrastructure for the entire subsequent mainline. It unifies the previously scattered rollout / cost / decode logic into a single CUDA evaluator that can be profiled, gated, made [persistent](https://zhida.zhihu.com/search?content_id=276233685&content_type=Article&match_order=1&q=%E6%8C%81%E4%B9%85%E5%8C%96&zhida_source=entity), and replayed via CUDA Graphs.

Another key significance of Stage-24 is that, when combined with the Stage-13B global-history exact path, it formed what later became known as the `exact_fused` path. This path satisfies two requirements simultaneously:

```text
1. Preserves the Stage-13B global-history exact semantics
2. Uses the Stage-24 fused evaluator for better execution efficiency
```

Therefore, although the later Stage-29 online/no-history experiments also tried to reduce history and cost accumulation overhead, because they deviated from the Stage-13B global-history exact semantics—and, in practice, were not faster than `exact_fused`—they could not become the production mainline. The production mainline ultimately returned to: Stage-13B global-history exact + Stage-24 fused. This is also the core issue that Stage-31 exact-first had to correct: one cannot treat online/no-history as the default path just because it looks “lighter.” The real default should be the Stage-24 fused exact evaluator.

From a performance standpoint, Stage-24 addresses the evaluator structure problem. It did not produce a sudden large jump the way Stage-34C5’s block-size tuning did, but it laid the foundation for all subsequent optimizations. Without the Stage-24 fused evaluator, the later native persistent, CUDA Graph, exact gate, and block sweep would have had difficulty forming a unified mainline.

Thus, Stage-24 can be understood as the “backbone-convergence phase” of the entire acceleration roadmap:

```text
Stage-17 / 18 proved that blindly increasing parallelism is unreliable;
Stage-20 / 23 cleaned up the CUDA rollout and engineering interfaces;
Stage-24 fixed the fused exact evaluator mainline;
Stage-29 verified that online/no-history cannot replace the exact path;
Stage-31 re-established exact-first;
Stage-30 / 34 all continued to squeeze performance around the Stage-24 exact_fused.
```

In other words, the key role of Stage-24 is not that it alone achieved all the acceleration, but that it determined which semantically correct, structurally stable CUDA evaluator mainline all subsequent acceleration efforts should revolve around.

## VI. Stage-30: Pushing All of ask/eval/tell into [C++](https://zhida.zhihu.com/search?content_id=276233685&content_type=Article&match_order=1&q=C%2B%2B&zhida_source=entity)/CUDA

The first key improvement that followed was Stage-30, the persistent native MEX optimizer.

Although the evaluator already ran in CUDA, a significant portion of the ask/eval/tell loop still involved MATLAB-layer scheduling. In each optimization generation, MATLAB had to generate or organize candidates, invoke the evaluator, retrieve costs, sort, and update the xNES distribution. This pattern was tolerable early on, but once the CUDA evaluator became fast, the MATLAB wrapper, gpuArray scheduling, temporary object creation, and host-device synchronization gradually turned into non-negligible overhead.

The goal of Stage-30 was to persist the optimizer state inside a native MEX:

```text
sim3_stage30_xnes_optimizer_mex('create', cfgPack, taskPack)
sim3_stage30_xnes_optimizer_mex('step', handle, x_current)
sim3_stage30_xnes_optimizer_mex('destroy', handle)
```

Persisted internally:

```text
RNG state
Z buffer
J buffer
elite index
xNES mean / std
workspace
paramPack / taskPack / costPack
CUDA stream
```

This way, each MPC control step no longer reconstructs a large number of temporary objects, nor does it frequently return to the MATLAB layer for ask/tell. More importantly, the optimizer state is retained across MPC steps, so warm-starting, RNG state, candidate buffers, and utility buffers can all be reused on the native side.

The purpose of this stage was not to change the exact evaluator, but to clean up outer-loop scheduling overhead. It addressed:

```text
MATLAB wrapper overhead
repeated GPU buffer allocation overhead
per-generation host-device synchronization
interpreter overhead in ask/tell
MATLAB involvement in sorting and utility updates
```

After Stage-30, ask/tell was no longer the primary bottleneck; eval became the true dominant term. This step mattered because only after clearing the outer-layer overhead could we accurately diagnose where the evaluator itself was slow.

## VII. Stage-34A: Native hotpath cleanup — removing per-generation host readback and full sort

Building on Stage-30, Stage-34A further cleaned up the native hotpath.

One critical issue: even if ask/eval/tell already ran inside MEX, if bestJ, bestIdx, and bestZ were still copied from device to host after every generation, the [GPU stream](https://zhida.zhihu.com/search?content_id=276233685&content_type=Article&match_order=1&q=GPU+stream&zhida_source=entity) would be forced to synchronize. A per-generation DeviceToHost readback would interrupt asynchronous execution and break the CUDA pipeline.

Stage-34A introduced several important changes:

```text
1. No longer copy bestJ / bestIdx / bestZ back to host every generation
2. Best candidate is continuously updated on the device side
3. Only one final D2H transfer after step completes
4. Replace Thrust full sort
5. Use small-pop topK / elite selection
6. Precompute rank utility at create time
```

This stage further demonstrated a key fact: for the current real-time MPC problem, an expensive general-purpose full sort is unnecessary. The optimizer only needs the elite ordering required by rank utility, so small-pop topK is better matched to the task scale.

However, measurements at this stage also showed: although the outer optimizer scheduling had been cleaned up, the dominant cost remained the exact evaluator. In other words, at this point one could no longer expect significant speedup from "reducing MATLAB scheduling" — the focus had to shift to the CUDA kernel itself and launch topology.

## VIII. Stage-34B / B2 / C1-3: CUDA Graph architecture and further diagnostics

The next step was CUDA Graph. In principle, CUDA Graphs can reduce kernel launch overhead, especially for repeated invocation of a fixed computational graph structure.

The native flow for each MPC control step is essentially fixed. Therefore, this fixed kernel sequence can be captured into a CUDA Graph, and then each MPC step only needs to update a few dynamic parameters and replay the graph. The Stage-34B initial version implemented capture / update / replay; Stage-34B2 further advanced it to a static CUDA Graph:

```text
capture once
index dynamic kernel nodes
patch dynamic params
replay many
```

The dynamic components include:

```text
x_current
DeltaL0
pb0x / pb0y
vb0x / vb0y
RNG iteration
```

These parameters are updated via patching kernel node params or a device stepPack, rather than reconstructing the entire graph each time. Architecturally this improvement was correct, but the performance gain was not obvious. The reason: each kernel in the current evaluator is already very heavy, so kernel launch overhead is not the main bottleneck.

CUDA Graph improved the architecture, making the native pipeline cleaner and more controllable. It proved that the problem was not launch scheduling, but the evaluator kernel itself and GPU occupancy.

To avoid blindly rewriting kernels, Stage-34C0 performed evaluator split profiling, providing guidance:

1.  Decode is not the bottleneck, so prioritizing direct-Z and removing the U workspace yields limited benefit.
2.  History write/initialization is not the bottleneck, so minimal-history should not be ranked first.
3.  Pure passive dynamics is not the entire bottleneck either; it is only part of the full exact evaluation. The remaining major cost more likely comes from release, hit, clear, contact/event logic, constraint/cost accumulation, and complex branching [state machine](https://zhida.zhihu.com/search?content_id=276233685&content_type=Article&match_order=1&q=%E7%8A%B6%E6%80%81%E6%9C%BA&zhida_source=entity) logic.

C2 mainly restructured the event/cost loop. The originally scattered loops for deterministic control cost, constraints, regularization, and jitter were merged into a single forward sweep. These terms were previously scanned across multiple loops over the horizon. After merging, the same horizon samples are still covered, the same costs are still accumulated, but repeated reads, repeated indexing, and repeated branching are reduced. C3 focused on mathematically equivalent micro-optimizations; none of these changes alter the mathematical semantics. Their goal was to reduce redundant computation inside the kernel, reduce [temporary variables](https://zhida.zhihu.com/search?content_id=276233685&content_type=Article&match_order=1&q=%E4%B8%B4%E6%97%B6%E5%8F%98%E9%87%8F&zhida_source=entity), and relieve register and local [memory access](https://zhida.zhihu.com/search?content_id=276233685&content_type=Article&match_order=1&q=%E8%AE%BF%E5%AD%98&zhida_source=entity) pressure.

These C2/C3 changes yielded modest gains, but no order-of-magnitude improvement. The reason is clear: this evaluator is a heavily branched, long-recurrence, one-thread-per-candidate physical kernel, and safe algebraic equivalent optimizations can only trim some redundancy.

## IX. 34C4: Block size / occupancy tuning — the key breakthrough

The most significant performance breakthrough that followed did not come from further algebraic manipulation, but from CUDA topology tuning, especially threadsPerBlock.

Previously, the default block size was relatively large — for example, 128, 160, 192, or 256. For ordinary lightweight kernels, large blocks are usually fine. But the current evaluator is a heavy-thread kernel:

```text
one thread = one full trajectory
long horizon loop inside each thread
high register usage
many local branches
many temporary variables
heavy contact / event logic
```

This type of kernel is highly sensitive to occupancy. When the block is too large, each block consumes excessive registers and scheduling resources, reducing the number of blocks/warps that can reside simultaneously on an SM, degrading latency-hiding capability — and paradoxically making it slower.

The block sweep results were very clear:

```text
threadsPerBlock ≈ 112 / 128: solve still near 0.22s
threadsPerBlock = 64: solve dropped to ~0.16s
threadsPerBlock = 32: solve further dropped to ~0.148s
```

This shows that the optimal CUDA topology for the current evaluator is not "larger blocks, more parallelism," but rather "smaller blocks, higher occupancy / better scheduling." In particular, 32 threads/block is essentially:

```text
one block = one warp
one warp contains 32 candidate threads
one thread still evaluates one candidate
```

This is not the Stage-18 style "one block = one trajectory." It still preserves candidate-level parallelism, but shrinks the block so the GPU can more flexibly schedule more lightweight blocks, reducing the occupancy loss caused by resource binding.

This finding is critical. It demonstrates that the truly effective optimization path is not to further split a single trajectory across [more threads](https://zhida.zhihu.com/search?content_id=276233685&content_type=Article&match_order=1&q=%E5%A4%9A%E7%BA%BF%E7%A8%8B&zhida_source=entity), but rather:

```text
keep one-thread-one-candidate
improve SM occupancy through block size tuning
reduce register-pressure constraints on resident block count
let the GPU better hide latency inside long serial trajectories
```

Each thread is currently very heavy. With 256 threads/block, one block contains 256 candidate trajectories. At first glance this seems like more parallelism, but each block also consumes far more registers in total. If register or local memory pressure is high, the SM can accommodate fewer resident blocks, leaving less scheduling space for warps.

With 32 threads/block, one block is exactly one warp. Although each block is smaller, the SM can place many more blocks simultaneously. For a kernel with heavy branching, long temporal recursion, and interleaved memory/compute operations, small blocks provide more [fine-grained](https://zhida.zhihu.com/search?content_id=276233685&content_type=Article&match_order=1&q=%E7%BB%86%E7%B2%92%E5%BA%A6&zhida_source=entity) scheduling units, making it easier for the SM to fill gaps.

In other words:

```text
large block = heavier individual block, coarser scheduling granularity, concentrated resource usage
small block = lighter individual block, finer scheduling granularity, easier to maintain occupancy
```

Because candidates are completely independent of each other — with no need for intra-block sharing or synchronization — using small blocks loses no algorithmic semantics and adds no synchronization cost. It simply changes the CUDA launch topology: how the GPU organizes these threads.

## X. Summary

This series of experiments ultimately demonstrates a core principle: GPU acceleration is not about "more threads equals faster," nor is it about "more aggressive parallelization equals faster." What actually matters is matching computational granularity, synchronization cost, register pressure, occupancy, and algorithmic semantics with each other.

Therefore, the most important lesson here is not "split the trajectory more finely," but:

-   Preserve candidate-level parallelism;
-   Avoid unnecessary synchronization;
-   Maintain exact evaluator and rank utility semantics;
-   Use native persistent + CUDA Graph to clean up outer scheduling;
-   Use small blocks to improve occupancy;
-   Use exact gates to confirm that every optimization does not change the natural gradient direction.

That is the truly effective CUDA acceleration path for this problem.
