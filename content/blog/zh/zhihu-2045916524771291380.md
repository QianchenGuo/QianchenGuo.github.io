[并行计算](https://zhida.zhihu.com/search?content_id=276233685&content_type=Article&match_order=1&q=%E5%B9%B6%E8%A1%8C%E8%AE%A1%E7%AE%97&zhida_source=entity)从理论上确实可以实现加速，但是实际上还需要考虑计算资源的调度以及[内存分配](https://zhida.zhihu.com/search?content_id=276233685&content_type=Article&match_order=1&q=%E5%86%85%E5%AD%98%E5%88%86%E9%85%8D&zhida_source=entity)的压力。所以并非[并行化](https://zhida.zhihu.com/search?content_id=276233685&content_type=Article&match_order=1&q=%E5%B9%B6%E8%A1%8C%E5%8C%96&zhida_source=entity)越彻底、简单加线程，算法运行就能越快。我们需要根据实际任务，匹配计算粒度、同步成本和 [GPU](https://zhida.zhihu.com/search?content_id=276233685&content_type=Article&match_order=1&q=GPU&zhida_source=entity) occupancy，来选择合适的[cuda](https://zhida.zhihu.com/search?content_id=276233685&content_type=Article&match_order=1&q=cuda&zhida_source=entity)拓扑及其参数。同时还应该尽可能减少各方的无用数据传输，这会占用大量时间。前者体现在stage17、18、34C4，后者则体现在stage24、30、34A。

## 一、[CUDA 拓扑](https://zhida.zhihu.com/search?content_id=276233685&content_type=Article&match_order=1&q=CUDA+%E6%8B%93%E6%89%91&zhida_source=entity)是什么？

CUDA 的执行层级大概是：

```text
Grid
  └── Block
        └── Warp
              └── Thread
```

对应到硬件上：

```text
GPU
  └── SM / streaming multiprocessor
        └── 同时调度多个 block / warp
              └── warp 内 32 个 thread 同步执行
```

最重要的概念是：

| 层级 | 作用 |
| --- | --- |
| thread | [线程](https://zhida.zhihu.com/search?content_id=276233685&content_type=Article&match_order=2&q=%E7%BA%BF%E7%A8%8B&zhida_source=entity)，最小[执行单元](https://zhida.zhihu.com/search?content_id=276233685&content_type=Article&match_order=1&q=%E6%89%A7%E8%A1%8C%E5%8D%95%E5%85%83&zhida_source=entity) |
| warp | 32 个 thread 一组，实际调度单位 |
| block | 一组 thread，可以共享 [shared memory](https://zhida.zhihu.com/search?content_id=276233685&content_type=Article&match_order=1&q=shared+memory&zhida_source=entity)，可以 \_\_syncthreads() |
| grid | 一次 [kernel](https://zhida.zhihu.com/search?content_id=276233685&content_type=Article&match_order=1&q=kernel&zhida_source=entity) launch 里的所有 block |
| SM | GPU 上真正执行 block/warp 的硬件单元 |

之前最快的主拓扑基本是：one thread = one candidate [trajectory](https://zhida.zhihu.com/search?content_id=276233685&content_type=Article&match_order=1&q=trajectory&zhida_source=entity)。也就是：k = blockIdx.x \* blockDim.x + threadIdx.x;每个 candidate 独立算一条轨迹。

如果 `K = 1536`，那就是 GPU 上同时有 1536 条轨迹可以并行。这个[粒度](https://zhida.zhihu.com/search?content_id=276233685&content_type=Article&match_order=2&q=%E7%B2%92%E5%BA%A6&zhida_source=entity)其实很适合 GPU，因为每条轨迹之间完全独立，不需要同步、不需要通信。

所以原来的[并行方式](https://zhida.zhihu.com/search?content_id=276233685&content_type=Article&match_order=1&q=%E5%B9%B6%E8%A1%8C%E6%96%B9%E5%BC%8F&zhida_source=entity)是：candidate-level parallelism  
优点：线程很多、同步很少、occupancy 比较好、每个 candidate 独立、调度简单；  
缺点：每条轨迹内部的 H 个时间步还是串行；每个时间步内部 passive dynamics 也是单线程算

## 二、Stage-17 为什么变慢？

Stage-17 主要是 aggressive launch/build profile：

```text
threads per block = 256
decode threads per block = 256
scan threads per block = 256
--use_fast_math
-O3
```

但它没有真正把核心 passive dynamics 变成协作式并行。也就是说，核心瓶颈仍然是：一个 thread 在串行算一条轨迹内部的 physics / passive dynamics

结果就是：[线程组织](https://zhida.zhihu.com/search?content_id=276233685&content_type=Article&match_order=1&q=%E7%BA%BF%E7%A8%8B%E7%BB%84%E7%BB%87&zhida_source=entity)更激进了、寄存器/局部内存压力更大了、occupancy 可能更差了、但真正的工作没有被有效并行拆开。

你的 Stage-17 日志正好证明了这一点：`balanced_h20` 验证里 `14B=1.1133s`，`17=1.1138s`，几乎没有加速；正常 [MPC](https://zhida.zhihu.com/search?content_id=276233685&content_type=Article&match_order=1&q=MPC&zhida_source=entity) 里反而明显变慢，`balanced_h20` 的 `MeanStepSolveSec=2.4835s`、`MeanObjCudaEvalCostSec=2.4666s`。这说明 Stage-17 改动主要增加了调度/资源压力，而不是减少了核心计算量。

简化理解：Stage-17 = 换了更激进的跑法，但没有真正改变最重计算的[算法结构](https://zhida.zhihu.com/search?content_id=276233685&content_type=Article&match_order=1&q=%E7%AE%97%E6%B3%95%E7%BB%93%E6%9E%84&zhida_source=entity)。所以它不但没解决问题，反而可能触发：[寄存器](https://zhida.zhihu.com/search?content_id=276233685&content_type=Article&match_order=2&q=%E5%AF%84%E5%AD%98%E5%99%A8&zhida_source=entity)溢出、[local memory](https://zhida.zhihu.com/search?content_id=276233685&content_type=Article&match_order=1&q=local+memory&zhida_source=entity) 访问增加、SM 上可同时驻留的 warp/block 减少、cache 行为变差

## 三、Stage-18 为什么变慢？

Stage-18 是真正开始面对核心问题了：把 passive dynamics 从：one thread = one trajectory改成：one block = one trajectory。128 threads 协作一条轨迹。这个方向理论上对，但你的实测说明：**当前 passive dynamics 的单步工作量还不足以摊平 128-thread block 的同步和占用成本。**

你测出来是：

```text
balanced:
scalar = 0.102s
block  = 0.273s
speedup = 0.375x

balanced_h20:
scalar = 0.128s
block  = 0.479s
speedup = 0.268x
```

这说明 block-coop 慢了 2.7 到 3.7 倍。

原因有几个：

1.  原因 A：时间递推本身不能并行。能并行的只是**每个时间步内部**的一部分计算，比如 beam/passive dynamics 里面的积分、矩阵装配、reduction。所以理论时间不是：T / 128。而更像：T\_new = 时间递推串行部分 + 每步内部并行部分 / 128 + 同步开销 + shared memory 开销 + occupancy 损失。如果每步内部能并行的那部分不够大，那么后面这些成本会超过收益。
2.  原因 B：128 threads/block 让 candidate [并行度](https://zhida.zhihu.com/search?content_id=276233685&content_type=Article&match_order=1&q=%E5%B9%B6%E8%A1%8C%E5%BA%A6&zhida_source=entity)下降。原来是：1 thread = 1 candidate。一个 128-thread block 可以同时容纳 128 个 candidate thread。现在变成：128 threads = 1 candidate。同样 128 个线程，只服务 1 条轨迹。这会让 GPU 同时处理的 candidate 数量大幅下降。虽然每条轨迹内部多了并行，但如果内部可并行工作不够大，就亏了。
3.  `__syncthreads()` 成本很高。block-coop passive solver 需要很多同步：\_\_syncthreads()；线程之间要协作写 shared memory、做 reduction、组装[矩阵](https://zhida.zhihu.com/search?content_id=276233685&content_type=Article&match_order=2&q=%E7%9F%A9%E9%98%B5&zhida_source=entity)，下一步必须等所有线程完成。如果每个 substep 都有多次同步，而 horizon 有 126 或 251 个 sample，那么同步成本会被放大很多。大概是：同步成本 × 每个时间步次数 × H × K。这个成本非常可观。
4.  实际矩阵规模太小。passive reduced dynamics 里很多[关键矩阵](https://zhida.zhihu.com/search?content_id=276233685&content_type=Article&match_order=1&q=%E5%85%B3%E9%94%AE%E7%9F%A9%E9%98%B5&zhida_source=entity)其实很小：这种东西不适合 128 个线程协作。比如 3x3 solve，总共才几个数。用 128 个线程做，会变成：大部分线程空等，thread 0 最后还是要串行 solve，其他线程等同步。所以这里不是线程越多越好，而是要匹配任务规模。
5.  shared memory / register 压力增加。block-coop 版本需要 shared memory 保存中间量：这些会增加每个 block 的资源占用。SM 资源有限：如果每个 block 太重，SM 上同时跑的 block 就少，occupancy 下降。结果是 GPU 没法用足吞吐。

## 四、正确并行是什么？

**Stage-17 增加了资源压力，但没真正并行化核心计算；Stage-18 真正并行化了核心计算的一部分，但[并行粒度](https://zhida.zhihu.com/search?content_id=276233685&content_type=Article&match_order=1&q=%E5%B9%B6%E8%A1%8C%E7%B2%92%E5%BA%A6&zhida_source=entity)太粗，128-thread block 的同步和 occupancy 损失超过了收益。**

不是退回去不并行，而是换成更合适的拓扑。one warp = one candidate trajectory

warp 是 32 个线程，不是 128 个线程。他比 128-thread block 同步成本低、比单 thread 有更多内部并行度、比 block-coop 占用更轻、warp 内可以用 shuffle 指令做 reduction、不一定需要大量 \_\_syncthreads()。拓扑变成：one block = 多个 warps，one warp = one trajectory 例如：128 threads/block = 4 warps/block = 4 trajectories/block。这比 Stage-18 好很多：Stage-18: 128 threads/block -> 1 trajectory/block；Stage-19: 128 threads/block -> 4 trajectories/block。这样既保留 candidate 并行，又有轨迹内部协作。

## 五、Stage-24 ：后续 exact 主线？

在 Stage-20 到 Stage-23 之间，主要工作还是围绕 CUDA rollout、workspace、static pack、history [buffer](https://zhida.zhihu.com/search?content_id=276233685&content_type=Article&match_order=1&q=buffer&zhida_source=entity) 和 [MATLAB](https://zhida.zhihu.com/search?content_id=276233685&content_type=Article&match_order=1&q=MATLAB&zhida_source=entity)\-CUDA 接口做工程整理。这些阶段解决了一些调用链和[数据搬运](https://zhida.zhihu.com/search?content_id=276233685&content_type=Article&match_order=1&q=%E6%95%B0%E6%8D%AE%E6%90%AC%E8%BF%90&zhida_source=entity)问题，但还没有真正改变 evaluator 的核心结构。真正让后续主线稳定下来的，是 Stage-24。

Stage-24 的核心思想是：

```text
fused decode + rollout + cost
```

也就是说，不再把[控制参数](https://zhida.zhihu.com/search?content_id=276233685&content_type=Article&match_order=1&q=%E6%8E%A7%E5%88%B6%E5%8F%82%E6%95%B0&zhida_source=entity)解码、轨迹积分、history 写入和 cost 计算拆成多个相互独立的 CUDA/MATLAB 阶段，而是尽可能在同一个 fused CUDA evaluator 里完成。

在此之前，典型流程更接近：

```text
Z compact 参数
  -> decode 成完整控制序列 U
  -> rollout dynamics
  -> 写 global history
  -> 再根据 history 计算 release / hit / clear / cost
```

这种拆分虽然逻辑清楚，但会带来几个问题：

```text
1. 中间 workspace 多
2. global memory 读写多
3. kernel launch 次数多
4. MATLAB/CUDA 调用边界多
5. 诊断和生产路径容易分叉
6. exact path 和 fast path 难以长期保持一致
```

Stage-24 做的事情，就是把这些过程尽量融合到一个 CUDA evaluator 路径中。候选参数 `Z` 被直接送入 fused evaluator，在 CUDA 内部完成控制解码、状态推进、release 判定、history 更新和 cost 累计。这样一来，主计算路径变成：

```text
Z compact
  -> Stage-24 fused decode-rollout-cost evaluator
  -> J
```

它的价值不只是“少几个 kernel launch”，更重要的是把 exact evaluator 的语义固定下来了。后续所有优化，包括 Stage-30 native persistent、Stage-34B2 CUDA [Graph](https://zhida.zhihu.com/search?content_id=276233685&content_type=Article&match_order=1&q=Graph&zhida_source=entity)、Stage-34C exact-preserving squeeze 和 block-size [调参](https://zhida.zhihu.com/search?content_id=276233685&content_type=Article&match_order=1&q=%E8%B0%83%E5%8F%82&zhida_source=entity)，都是围绕这个 Stage-24 fused exact evaluator 展开的。

也就是说，Stage-24 是后续主线的基础设施。它把原来分散的 rollout / cost / decode 逻辑统一到一个可 profile、可 gate、可[持久化](https://zhida.zhihu.com/search?content_id=276233685&content_type=Article&match_order=1&q=%E6%8C%81%E4%B9%85%E5%8C%96&zhida_source=entity)、可 graph replay 的 CUDA evaluator 里。

Stage-24 的另一个重要意义是，它和 Stage-13B global-history exact path 结合后，形成了后续所谓的exact\_fused path。这条路径同时满足两个要求：

```text
1. 保持 Stage-13B global-history exact 语义
2. 使用 Stage-24 fused evaluator 提高执行效率
```

因此，后面 Stage-29 的 online/no-history 实验虽然也尝试减少 history 和 cost 累计开销，但由于它偏离了 Stage-13B global-history exact 语义，而且实测并没有比 exact\_fused 更快，所以不能成为生产主线。生产主线最后还是回到了：Stage-13B global-history exact + Stage-24 fused。这也是后来 Stage-31 exact-first 要纠正的核心问题：不能因为 online/no-history 看起来更“轻”，就把它当默认路径。真正应该固定为主线的是 Stage-24 fused exact evaluator。

从性能角度看，Stage-24 解决的是 evaluator 结构问题。它没有像 Stage-34C5 的 block-size 调参那样突然带来巨大跳变，但它把后续所有优化的地基搭好了。没有 Stage-24 的 fused evaluator，后面的 native persistent、CUDA Graph、exact gate、block sweep 都很难形成统一主线。

因此，Stage-24 可以理解为整个加速路线里的“主干收敛阶段”：

```text
Stage-17 / 18 证明盲目增加并行度不可靠；
Stage-20 / 23 整理 CUDA rollout 和工程接口；
Stage-24 固定 fused exact evaluator 主线；
Stage-29 验证 online/no-history 不能替代 exact path；
Stage-31 重新确立 exact-first；
Stage-30 / 34 后续都围绕 Stage-24 exact_fused 继续压榨。
```

换句话说，Stage-24 的关键性不在于它单独完成了所有加速，而在于它确定了后续所有加速都应该围绕哪条语义正确、结构稳定的 CUDA evaluator 主线展开。

## 六、Stage-30：把 ask/eval/tell 全部推进 [C++](https://zhida.zhihu.com/search?content_id=276233685&content_type=Article&match_order=1&q=C%2B%2B&zhida_source=entity)/CUDA

后续第一项关键改进是 Stage-30 persistent native MEX optimizer。

之前虽然 evaluator 已经在 CUDA 中执行，但[优化器](https://zhida.zhihu.com/search?content_id=276233685&content_type=Article&match_order=1&q=%E4%BC%98%E5%8C%96%E5%99%A8&zhida_source=entity)的 ask/eval/tell 流程仍然有较多 MATLAB 层调度参与。每一代优化里，MATLAB 需要生成或组织候选、调用 evaluator、拿回 cost、排序、更新 xNES 分布。这种模式在早期可以接受，但当 CUDA evaluator 已经很快时，MATLAB wrapper、gpuArray 调度、临时对象创建和 host-device 同步就会逐渐变成不可忽略的开销。

Stage-30 的目标是把优化器状态持久化到 native MEX 里：

```text
sim3_stage30_xnes_optimizer_mex('create', cfgPack, taskPack)
sim3_stage30_xnes_optimizer_mex('step', handle, x_current)
sim3_stage30_xnes_optimizer_mex('destroy', handle)
```

内部持久保存：

```text
RNG state
Z buffer
J buffer
elite index
xNES mean / std
workspace
paramPack / taskPack / costPack
CUDA stream
```

这样每个 MPC 控制步不再重新构造大量临时对象，也不再频繁回到 MATLAB 层做 ask/tell。更重要的是，优化器状态跨 MPC step 保留，warm-start、随机数状态、候选 buffer、utility buffer 都可以在 native 侧复用。

这个阶段的作用不是改变 exact evaluator，而是把外层调度开销清理干净。它解决的是：

```text
MATLAB wrapper 开销
反复分配 GPU buffer 的开销
每 generation host-device 同步
ask/tell 的解释器开销
排序和 utility 更新的 MATLAB 参与
```

Stage-30 之后，ask/tell 基本不再是主瓶颈，eval 才成为真正主导项。这一步很重要，因为只有把外层开销清掉，后续才能准确判断 evaluator 本身到底慢在哪里。

## 七、Stage-34A：native hotpath cleanup，去掉 per-generation host readback 和 full sort

在 Stage-30 基础上，Stage-34A 进一步清理 native hotpath。

一个关键问题是：即使 ask/eval/tell 已经在 MEX 内部，如果每个 generation 结束后仍然把 bestJ、bestIdx、bestZ 从 device 拷回 host，那么 [GPU stream](https://zhida.zhihu.com/search?content_id=276233685&content_type=Article&match_order=1&q=GPU+stream&zhida_source=entity) 会被强制同步。每代一次的 DeviceToHost readback 会打断异步执行，破坏 CUDA pipeline。

Stage-34A 做了几个重要改动：

```text
1. 不再每 generation 把 bestJ / bestIdx / bestZ 拷回 host
2. best candidate 在 device 侧持续更新
3. step 结束后只做一次最终 D2H 回传
4. 替换 Thrust full sort
5. 使用 small-pop topK / elite selection
6. rank utility 在 create 阶段预计算
```

这一阶段进一步说明了一个事实：对于当前实时 MPC 问题，没有必要做昂贵的通用 full sort。优化器只需要 rank utility 所需的 elite 顺序，因此 small-pop topK 更符合任务规模。

但这一阶段的实测也说明：外层优化器调度虽然被清理了，真正大头仍然是 exact evaluator。也就是说，此时已经不能再指望通过“减少 MATLAB 调度”获得大幅加速，必须进入 CUDA kernel 本体和 launch 拓扑层面。

## 八、Stage-34B / B2/ C1-3：CUDA Graph 架构化与进一步诊断

下一步是 CUDA Graph。理论上，CUDA Graph 可以减少 kernel launch overhead，尤其适合固定计算图结构的反复调用。

MPC 每个 control step 的 native 流程基本固定。因此可以把这个固定 kernel 序列 capture 成 CUDA Graph，然后每个 MPC step 只更新少量动态参数并 replay graph。Stage-34B 初版实现了 capture / update / replay；Stage-34B2 进一步做成 static CUDA Graph：

```text
capture once
index dynamic kernel nodes
patch dynamic params
replay many
```

动态变化的内容包括：

```text
x_current
DeltaL0
pb0x / pb0y
vb0x / vb0y
RNG iteration
```

这些参数通过 patch kernel node params 或 device stepPack 更新，而不是每次重新构造整个 graph。这个改进在架构上是正确的，但性能收益并不明显。原因是当前 evaluator 每个 kernel 本身非常重，kernel launch overhead 不是主要矛盾。

CUDA Graph 改善了架构，使 native pipeline 更干净、更可控，它证明问题不在 launch 调度，而在 evaluator kernel 本体和 GPU occupancy。

为了避免盲目重写 kernel，Stage-34C0 做了 evaluator split profiling给出指导

1.  decode 不是瓶颈，所以优先做 direct-Z、去掉 U workspace 的收益有限。
2.  history 写入/初始化不是瓶颈，所以 minimal-history 不应该排在最前。
3.  纯 passive dynamics 也不是全部瓶颈，它只是 full exact 的一部分。剩下的大头更可能来自 release、hit、clear、contact/event logic、constraint/cost accumulation 和复杂分支[状态机](https://zhida.zhihu.com/search?content_id=276233685&content_type=Article&match_order=1&q=%E7%8A%B6%E6%80%81%E6%9C%BA&zhida_source=entity)。

C2 主要做 event/cost loop restructure。把原本分散的 deterministic control cost、constraint、regularization、jitter 等循环合并为一次 forward sweep。这些项原本可能在多个 loop 中分别扫描 horizon。合并后，仍然覆盖同样的 horizon sample，仍然累积同样的 cost，只是减少重复读取、重复索引和重复分支。C3 主要做数学等价微优化，这些改动都不改变数学语义。它们的目标是减少 kernel 内部重复运算、减少[临时变量](https://zhida.zhihu.com/search?content_id=276233685&content_type=Article&match_order=1&q=%E4%B8%B4%E6%97%B6%E5%8F%98%E9%87%8F&zhida_source=entity)、减少寄存器和局部[访存](https://zhida.zhihu.com/search?content_id=276233685&content_type=Article&match_order=1&q=%E8%AE%BF%E5%AD%98&zhida_source=entity)压力。

这些 C2/C3 改动带来了小幅收益，但没有[数量级](https://zhida.zhihu.com/search?content_id=276233685&content_type=Article&match_order=1&q=%E6%95%B0%E9%87%8F%E7%BA%A7&zhida_source=entity)变化。原因也很明确：该 evaluator 是一个重分支、长时间递推、one-thread-per-candidate 的复杂物理 kernel，安全的代数等价优化只能压掉一些冗余。

## 九、34C4 block size / occupancy调参：关键突破

后续最关键的性能突破不是来自继续改数学[表达式](https://zhida.zhihu.com/search?content_id=276233685&content_type=Article&match_order=1&q=%E8%A1%A8%E8%BE%BE%E5%BC%8F&zhida_source=entity)，而是来自 CUDA 拓扑调参，尤其是 threadsPerBlock。

之前默认 block size 较大，比如 128、160、192、256。对普通轻量 kernel 来说，大 block 往往没问题。但当前 evaluator 是重 thread kernel：

```text
one thread = one full trajectory
每个 thread 内部有长 horizon 循环
寄存器使用多
局部分支多
临时变量多
contact / event logic 重
```

这种 kernel 对 occupancy 非常敏感。block 太大时，每个 block 消耗过多寄存器和调度资源，SM 上可同时驻留的 block/warp 数下降，延迟隐藏能力变差，反而变慢。

block sweep 的结果非常清楚：

```text
threadsPerBlock = 112 / 128 附近，solve 仍然接近 0.22s
threadsPerBlock = 64，solve 降到约 0.16s
threadsPerBlock = 32，solve 进一步降到约 0.148s
```

这说明当前 evaluator 的最佳 CUDA 拓扑不是“大 block 更并行”，而是“小 block 更高 occupancy / 更好调度”。尤其是 32 threads/block 本质上接近：

```text
one block = one warp
one warp contains 32 candidate threads
one thread still evaluates one candidate
```

这不是 Stage-18 那种“one block = one trajectory”。它仍然保留 candidate-level parallelism，但把 block 调小，让 GPU 能更灵活地调度更多轻量 block，降低资源绑定带来的 occupancy 损失。

这个发现非常关键。它说明后续真正有效的优化路径不是继续把单条轨迹拆给更[多线程](https://zhida.zhihu.com/search?content_id=276233685&content_type=Article&match_order=1&q=%E5%A4%9A%E7%BA%BF%E7%A8%8B&zhida_source=entity)，而是：

```text
保留 one-thread-one-candidate
通过 block size 调整改善 SM occupancy
减少 register-pressure 对驻留 block 数的限制
让 GPU 更好地隐藏长串行 trajectory 内部的延迟
```

当前每个 thread 很重。如果使用 256 threads/block，一个 block 里有 256 条 candidate trajectory。看似并行更多，但每个 block 消耗的寄存器总量也更大。如果寄存器或 local memory 压力高，SM 同时能驻留的 block 数就少，warp 调度空间变小。

而 32 threads/block 时，一个 block 正好一个 warp。虽然每个 block 更小，但 SM 可以同时放入更多 block。对于这种分支多、时间递推长、访存和计算交织的 kernel，小 block 能提供更[细粒度](https://zhida.zhihu.com/search?content_id=276233685&content_type=Article&match_order=1&q=%E7%BB%86%E7%B2%92%E5%BA%A6&zhida_source=entity)的调度单位，让 SM 更容易填满空隙。

换句话说：

```text
大 block = 单个 block 更重，调度粒度粗，资源占用集中
小 block = 单个 block 更轻，调度粒度细，occupancy 更容易维持
```

由于每个 candidate 之间完全独立，不需要 block 内共享和同步，因此使用小 block 不会损失算法语义，也不会增加同步成本。它只是在改变 CUDA launch topology。改变了 GPU 如何组织这些 thread。

## 十、总结

这一系列实验最终说明了一个核心原则：GPU 加速不是线程越多越快，也不是并行化越彻底越快；真正有效的是把计算粒度、同步成本、寄存器压力、occupancy 和算法语义匹配起来。

因此，目前最重要的经验不是“把轨迹内部拆得更细”，而是：

-   保留 candidate-level parallelism；
-   避免不必要同步；
-   保持 exact evaluator 和 rank utility 语义；
-   用 native persistent + CUDA Graph 清理外层调度；
-   用小 block 提高 occupancy；
-   通过 exact gate 确认每一步优化不改变自然梯度方向。

这才是当前问题上真正有效的 CUDA 加速路线。
